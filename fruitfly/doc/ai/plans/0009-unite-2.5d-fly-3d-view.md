# Plan 0009 — Unite: a fly that flies to the banana in 2.5D (+ a real 3D view)

**Status:** Built — the union, the headless proof, and the Godot **3D** view (Play 9) all land; one
honest gap documented below. Both halves of flight were built and honest but SEPARATE: horizontal
(the 2D `Fly` — seek/avoid/memory) and vertical (`FlyingBody` — wingbeat lift, hover reflex,
climb-to-food). This unites them into one creature and shows it in a Godot **3D** scene. Build order:
the unified creature **headless first**, then the 3D view (the same isolate-then-visualise path used
throughout).

**Honest status (what's proven vs. what's not):**
- ✅ **The 2.5D union works.** A `fly3D:true` `Fly` owns a `FlyingBody`; the vertical layer is *perfect*
  — the headless check nails the banana's **height (gap ≈ 0px) in every one of 25 trials**.
- ✅ **The 3D view is alive** (`Fly3DView` + `FlyBrainOverlay`): antennae that flare on touch, a smell
  aura, altitude shadow + drop-line, motion trail, following camera, and a live brain+flight HUD.
- ✅ **Checks made honest.** The fly is stochastic (membrane noise = `Random.Shared`), so single-run
  pass/fail was a coin-flip. Both headless checks now run **25 trials** and assert the *population*:
  the 2D fly always moves and the memory **always** frees it (worst jam ~8s, never permanent).
- ⚠️ **Reliable EATING is NOT achieved — a pre-existing 2D trait, not a 2.5D fault.** The horizontal
  brain **orbits the banana at ~43px, just outside the 42px eat radius** (smell sensors saturate near
  the source → steering dies → momentum rings it), so it eats only ~1 banana / 45s. We never measured
  2D *eating* before (the 2D check tests *escape*). The 3D check is intentionally **RED** with this
  recorded. **TODO (brain change, deferred):** de-saturate the horizontal smell-seek so it spirals IN
  / slows on approach — **not** by widening the eat radius to cross 1px (that would be a fudge).
**Goal:** One creature that approaches the banana in **X/Y** (existing chemotaxis + wall-avoidance +
memory) while **climbing to its height** on a self-generated wingbeat (existing lift + hover +
vertical chemotaxis), and **eats it in 3D** — watchable as a fly flying through space.

## Why now

Everything points here. The 2D fly seeks a banana on a plane; the flying body seeks a height and
holds itself up. The banana is the shared goal — it just needs a *height*. Uniting is mostly
*composition* of two things we already trust, and it finally earns the **3D view** the user wanted
from the start (ADR 0004's eventual dual-view, now in 3D).

## The honest simplification (state it plainly)

In this rung, **forward** locomotion stays the 2D "wings-as-effectors" Braitenberg abstraction (same
as today's fly), while **lift / altitude** is the honest self-generated wingbeat. The thing that
physically unifies them — the body **pitching** so one wing-force vector splits into lift + thrust —
is the *next* rung (deferred, documented). So this is no *less* honest than the current 2D fly; it
adds an honest vertical axis on top. We say so in the code and the view, and we don't pretend the
forward thrust comes from the beat yet.

## Approach — composition, leave the proven parts untouched

- **`Fly` gains an OPT-IN vertical layer.** A `Fly` built in 3D mode owns a `FlyingBody` for its
  altitude and tells it to `SeekAltitude(bananaHeight)` each step; a `Fly` built in 2D mode (Play 6)
  is byte-for-byte unchanged. The proven horizontal brain/body is not touched.
- **The banana gains a height.** `World` keeps its 2D smell field and walls (horizontal) and adds a
  banana **height** (respawns at a random height too). Eating becomes **3D proximity** — near in X/Y
  *and* near in height.
- **The 3D view is a pure viewer.** A Godot `Node3D` scene reads the creature's 3D position +
  heading and places meshes (fly, banana, ground, walls). No brain/body logic in the view (ADR 0005).

## Steps (tiny pieces — assistant writes, one at a time)

- [x] **World: the banana gets a height** — a `BananaHeight` that respawns randomly with it, and a
      3D-aware eat (`TryEat` considers altitude). 2D callers (Play 6) keep working. *(Respawn was
      split into `RespawnXY` + a 3D-only height draw so the 2D path consumes NO extra RNG — a 2D world
      has no height axis, and it keeps Play 6's seeded check byte-for-byte.)*
- [x] **Fly: opt-in vertical layer** — compose a `FlyingBody`, `SeekAltitude(world.BananaHeight)`,
      advance it each step, expose `Altitude`/`BeatVigor`/`WingbeatPhase`; eat when close in 3D.
      Proven headless: it nails the height every trial. *(Eating in X/Y is the orbit gap above.)*
- [x] **Godot 3D view** — `Fly3DView` (`Node3D`): ground, four walls, banana sphere at its 3D spot,
      the fly mesh at position + heading + altitude, lighting + following camera. Plus life: antennae
      that flare on touch, a smell aura, altitude shadow + drop-line, a motion trail. The fly is a
      proper lumpy brown *Drosophila* (red eyes, swept hinged wings that beat with big amplitude).
      **Honest caveat:** those beating wings are a faithful *readout* of the real neural wingbeat
      oscillator (and that beat's vigour really makes the vertical lift) — but the wing meshes are NOT
      aerodynamically simulated (lift = vigour×gain, both wings mirror one phase scalar, and they add
      nothing to horizontal motion). They show the beat; they don't compute its forces.
- [x] **brain/altitude HUD** — `FlyBrainOverlay` (2D overlay): the Play-6 brain meters (SMELL/TOUCH/
      WINGS/MEMORY/NOCI) **plus** the vertical signals (LIFT, ALT, CLIMB), so the thinking stays visible.

## Open questions to resolve with the user (when we hit them)

- **Coupling.** Keep horizontal and vertical seeking fully independent (simplest), or couple them
  (e.g. ease off forward speed while still far below the banana's height)? Start independent.
- **3D view scope.** Fixed camera vs. follow-cam; how much fly detail (a body + flapping wings vs. a
  simple arrow); do walls/floor get textures or stay flat-shaded? Start minimal and flat.
- **Where the unified creature lives.** Extend `Fly` (recommended — composition, opt-in) vs. a new
  `FlyingFly` type. Extending keeps one fly and avoids duplication.

## Done when

The fly **flies to the banana through 3D space** — seeking it horizontally while climbing to its
height on its own wingbeat — and eats it, watchable in a Godot 3D scene. The user can explain which
parts are honest wingbeat-flight (lift, altitude-hold, vertical seeking) and which are still the 2D
abstraction (forward thrust), and why **pitch** is the next step to make forward flight true.

**Reached, with one carve-out:** it *flies to* the banana in 3D (height nailed every trial, homes in
horizontally) and is watchable + alive in Play 9 — but **reliable eating** waits on the horizontal
orbit fix (see Honest status). That fix is really the **Coupling** open question below: a fly that
slows / tightens as it nears the source (de-saturated seek) would both stop orbiting AND make the two
axes converge together.
